# 通用互联网/云原生 AIOps

## 领域定义

IBM 对 AIOps 的定义可以作为产业界基准：将 AI、NLP、机器学习用于自动化、优化 IT 服务管理和运维流程；核心动作包括聚合海量运维数据、从噪声里识别信号、诊断根因、辅助或自动修复。

在工程上，AIOps 的输入通常包括：

- 指标：CPU、内存、网络、延迟、错误率、业务 KPI。
- 日志：应用日志、系统日志、审计日志、异常栈。
- 链路：trace/span、调用拓扑、依赖关系。
- 事件：告警、发布、变更、扩缩容、配置变更。
- 工单：事故描述、分派过程、修复动作、复盘。
- 知识：Runbook、TSG、架构文档、值班经验。

## 典型任务

1. 异常检测：发现指标、日志、链路或业务 KPI 偏离正常状态。
2. 告警降噪：合并重复告警、去除低价值告警、识别主告警。
3. 根因定位：定位服务、实例、机器、代码变更、配置变更或依赖故障。
4. 事故分派：找到正确 owner/team，减少转派和等待。
5. 影响评估：判断用户影响、SLO 影响、业务损失。
6. 修复建议：生成 Runbook 步骤、缓解动作、回滚建议。
7. 自动缓解：扩容、重启、隔离、流量切换、回滚、限流。
8. 复盘沉淀：生成 postmortem、抽取 action item、更新知识库。

## 代表性论文脉络

### 日志智能

DeepLog, CCS 2017：把系统日志视为序列，用 LSTM 学习正常日志模式，偏离模式即异常，并尝试从日志工作流支持诊断。它奠定了“日志序列建模”的经典路线。

Drain, ICWS 2017：在线日志解析方法，用固定深度树把非结构化日志转成模板，是后续日志异常检测的常用前处理。

LogAnomaly, IJCAI 2019：用 template2vec 抽取日志模板语义，同时检测日志序列异常和数量异常，强调新日志模板导致误报的问题。

LogRobust, FSE 2019：指出真实生产日志不是封闭稳定集合，日志语句会演进、解析会有噪声，因此用语义向量和 attention Bi-LSTM 处理不稳定日志。

### 时间序列与指标异常检测

Microsoft KDD 2019 Time-Series Anomaly Detection Service：工业级在线服务，强调准确、高效、通用，提出 SR-CNN 组合方法，并在公开数据和 Microsoft 生产数据上验证。

OmniAnomaly, KDD 2019：面向多变量时间序列，用随机循环神经网络、VAE/normalizing flow 学习正常模式，并能给出维度级解释。它对服务器、航天器、发动机等多传感器实体都有启发。

### 根因定位与微服务诊断

CloudRanger, CCGrid 2018：从 IBM Bluemix 真实事故出发，在未知拓扑条件下学习动态因果影响图，用二阶随机游走识别故障服务。

MicroRCA, NOMS 2020：面向 Kubernetes 微服务，结合应用性能症状和资源指标构造 attributed graph，实时定位性能问题根因。

Narya, OSDI 2020：Azure 生产系统里的主动故障缓解服务，预测主机故障并选择缓解动作，使用在线实验和强化学习，在 15 个月生产运行中平均降低 VM 中断。

### LLM4AIOps

Microsoft Research 近年集中发表了大量 LLM + AIOps 工作：事故摘要、事故分派、查询推荐、自动日志、可解释 incident triage 等。ICSE 2024 的 UniLog 和 Xpert、ISSRE 2024 的 incident triage、ESEC/FSE 2023 的 outage summarization 都说明：LLM 正在从“写总结”走向“参与事故生命周期”。

Meta 2024 公开的 AI-assisted RCA 系统代表了工业界务实路线：先用启发式检索把代码变更候选从几千降到几百，再用微调 Llama 排序 top-5 根因候选；系统在 web monorepo 历史事故回测中达到 42% top-5 命中。

## 当前难点

1. 数据质量：日志字段不统一、指标口径混乱、trace 采样缺失、告警规则历史包袱重。
2. 标注稀缺：真实事故少、标签粗、根因多义、复盘质量不稳定。
3. 分布漂移：服务频繁发布、架构变化、流量周期性变化、告警策略变化。
4. 评估困难：离线 F1 不等于线上 MTTR 降低；真实世界更关注 precision、top-k、人工节省时间和误导风险。
5. 自动处置风险：错误修复可能扩大事故，因此需要审批、灰度、回滚、权限边界和审计。
6. 组织协作：AIOps 不是模型团队单独能做成，必须嵌入 SRE、平台、业务和安全流程。

## 工程架构参考

一个现实可落地的通用 AIOps 系统通常有以下层次：

1. 数据接入层：OpenTelemetry、Prometheus、Loki/ELK、Jaeger/Tempo、Kafka。
2. 数据湖/数仓层：ClickHouse、Druid、Elastic、Hudi/Delta Lake、对象存储。
3. 语义建模层：指标字典、服务拓扑、CMDB、资源图谱、变更图谱、告警本体。
4. 算法层：异常检测、事件聚合、RCA 排序、影响评估、预测。
5. Agent 层：RAG、工具调用、Runbook 执行、沙箱分析、报告生成。
6. 控制层：权限、审批、审计、回滚、灰度、SLO/错误预算约束。
7. 人机协同层：值班台、ChatOps、复盘平台、知识库。

## 对你的启发

通用 AIOps 的学习不要只盯模型榜单。你要始终问三个问题：

1. 这个模型需要什么数据？真实生产是否拿得到？
2. 这个输出能让 SRE 少做哪一步？是发现、判断、分派、定位还是修复？
3. 如果模型错了，系统怎么限制损失？
